# План разработки Git Workspace для Orca

Основа: [ARCHITECTURE.md](ARCHITECTURE.md). UX-референс: предоставленный пользователем popup JetBrains со списком репозиториев и меню веток выбранного репозитория.

Статус: этапы 0–7 выполнены в проверенной локальной среде. В `./orca` реализованы host-авторизованный рекурсивный каталог Git-контекстов, status, существующий IPC/RPC/preload, Changes/diff, popup контекстов/refs, частичный stage/unstage, commit/discard, история и явные ветки/remotes/merge/rebase. Этап 7 добавляет обслуживание сабмодулей с offline-preview и явной рекурсией, безопасные add/remove и пакеты commit/publish от листьев к корню с подтверждением точных gitlink OID и проверкой доступности дочерних commit на remote назначения. Доказательства и ограничения — в ARCHITECTURE.md и STAGE1–STAGE7-REPORT.md. По указанию пользователя остановка перед этапами 8–9: они не начаты; commit/push и продолжение ожидают отдельного согласования с сессией публикации.

## Конечный результат

Внутри Orca доступны Changes, качественный diff, частичные коммиты, история с графом, ветки/remotes и разрешение конфликтов. Корень и сабмодули любой обнаруженной вложенности используют одинаковые возможности, без ручной регистрации каждого сабмодуля как отдельного проекта.

Основной вход — быстрый переключатель из индикатора ветки: список репозиториев с их ветками/состояниями, поиск и меню выбранного контекста. Панель Submodules дополняет его подробным обзором и операциями обслуживания.

Без IntelliJ Platform, отдельной JVM, собственного Git-движка и облачного посредника. Развиваем существующие Git/diff-возможности Orca, не создаём параллельную интеграцию.

## Правила исполнения

- Каждый этап включает backend, транспорт и пользовательскую поверхность в необходимом объёме; законченный backend без работающего сценария UI не считается завершением этапа.
- Git выполняется на execution host соответствующего checkout. Для локальных и удалённых контекстов применяется одна модель прав и идентичности.
- Реальный Git index определяет состав коммита. Выбор контекста не переключает ветку; commit родителя не коммитит дочерние репозитории.
- UI не исполняет shell и не присылает произвольный patch. Host проверяет контекст, аргументы и ожидаемое состояние.
- Внешние агенты и CLI могут менять Git одновременно. Проверки состояния и Git locks не выдаются за глобальную транзакцию.
- Просмотр не запускает незаметный fetch/clone. Неизвестные потомки неинициализированного сабмодуля явно обозначаются как необнаруженные.
- Нет скрытого stash, автоматического force, `reset --hard`, `clean` и повторного commit/push после неизвестного результата.
- Каждый этап завершается smoke-прогоном настоящего UI и проверкой реального Git-состояния. Тесты не заменяют этот прогон.
- После проверки изменения обновляются существующие документация/changelog Orca; временные проверочные материалы удаляются. Устаревшие пути удаляются после миграции всех их потребителей.

### Фактический результат этапа 4

- Все записи Source Control корня и дочерних checkout идут через host-сервис `mutateGitWorkspace` и транспорт `git.mutate`/`git:mutate` (RPC, IPC, preload, web-preload, renderer-клиент). Host выдаёт `documentId`/`hunkIds`/`lineIds`, сам строит patch по выбранным строкам и применяет его к реальному index; renderer не присылает patch и не получает полномочий из пути.
- Partial staging поддерживает чистые addition/delete-блоки по строкам; замена и блок с отсутствующим final newline перемещаются вместе, чтобы не дублировать строку и не создавать невозможную границу newline. Rename, binary, >8 MiB, non-UTF-8, symlink, mode-only и unmerged частично не поддерживаются и явно предлагают файловые операции. Rename stage/unstage действует на оба пути.
- Перед записью проверяются авторизованный контекст, `expectedState` (HEAD/index/status + index records) и content fence (HEAD, index-записи и байты worktree; >16 MiB — filesystem identity). Stale/failed fence не применяется к новому содержимому; UI перечитывает фактическое состояние.
- Одна очередь по process + common git-dir сериализует все Orca-записи, включая linked worktrees и существующие bulk-маршруты. Внешние писатели не блокируются; Git locks и fences только обнаруживают конфликт, транзакция не обещается.
- Commit использует ровно реальный index и preview staged-набора; hooks и signing не отключаются. Ошибка hook/signing показывается с текстом Git и свежим состоянием; hook, изменивший index, виден в коммите. Обрыв/отмена после старта процесса даёт `unknown` без автоматического повтора. Дочерние контексты имеют собственный commit-surface и черновик сообщения по context ID.
- Discard имеет preview, host token, подтверждение и копию+manifest под `<gitDir>/orca-recovery`; при недоступности копии действие отклоняется. Untracked новым путём не удаляются; `restoreDiscard` возвращает копию только при неизменённом файле, `listRecoveries` показывает доступные копии.
- `stageGitlink` проверяет child OID, child HEAD, child context и parent index, пишет только gitlink и перечитывает запись; child index/HEAD/файлы не меняются, parent commit не коммитит child.
- Проверки: backend real Git **23 passed**, broad regression **252 passed / 22 files**, stage-3 suite **141 passed**, новые UI-тесты **5 passed**, web tsc/catalog/targeted oxlint — exit 0, Electron build exit 0 (176 chunks), настоящий Electron **5 passed дважды** (stage-4 root+child + diff/popup/catalog/golden). Точные команды, acceptance-сценарии и пределы — в STAGE4-REPORT.md.
- Пределы: проверен только локальный macOS host, не SSH/WSL/Windows и не release package; root commit сохраняет прежний per-worktree контракт без `expectedState` (дочерний commit проверяется полностью); freshness >16 MiB использует filesystem identity; recovery-копии не GC-ятся; полный tsc node/CLI сохраняет прежние ошибки вне stage-4 файлов. Этап 5 не начинался.

Gitlink diff получил переход `Open child Log`; Open Log также доступен из popup и заголовка Changes.

Корень сохраняет прежнюю combined-diff поверхность; у дочернего контекста «Open all changes» не показывается, файлы открываются по одному.
- Пределы: страница 50 (максимум 200), не более 5000 уже загруженных коммитов (`--skip`), виртуализация с фиксированной высотой строки; проверен только локальный macOS Electron, не SSH/WSL/Windows и не release package. Точные команды, evidence и ограничения — в STAGE5-REPORT.md. Этап 6 не начинался.

### Фактический результат этапа 6

- **Один backend.** `mutateGitWorkspace` получил `checkout`, `createBranch`, `fetch`, `push`, `merge`, `rebase`, `continueOperation`, `abortOperation`; они используют существующие `git.mutate`/`git:mutate`, preload/web client, context authorization и очередь по common git-dir. Второго backend, обхода fences или path-as-authority нет.
- **Fences.** Checkout/New Branch/merge/rebase/continue/abort требуют `expectedHead` (пустая строка для unborn) и сверяют его после повторного discovery; push требует `expectedRefOid` и сверяет OID ветки. `fetch` не пишет worktree/index. `expectedState` остаётся контрактом stage 4. Branch occupancy проверяется по `worktree list --porcelain -z` (включая реальный путь), dirty — по пересечению entries с `diff --name-only HEAD <target>`, поэтому несвязанные локальные изменения не блокируются.
- **Checkout.** Local branch — короткое имя (полный ref отсоединил бы HEAD); remote branch создаёт локальную с `--track`; tag/полный OID — detached. New Branch проверяет имя через `check-ref-format`, создаёт и переключает; старт с remote ref ставит tracking. Автоматического stash/force/`reset --hard`/`clean` нет.
- **Refs и актуальность.** `GitWorkspaceRef` содержит upstream, ahead/behind и upstreamGone из локального `%(upstream:track)`; `RepositoryState` — `refsReadAt`, `lastFetchAt` (mtime `FETCH_HEAD`) и имена remotes без URL. UI прямо указывает, что это данные загруженных refs и fetch автоматически не выполняется.
- **Fetch/push.** Remote обязан быть в `git remote`; URL не принимается. Аргументы: `fetch --progress --prune --no-recurse-submodules <remote> [<branch>]`, `push --progress --no-recurse-submodules [--set-upstream] <remote> <ref>:<ref>`, timeout 300 s. Используются SSH/credential-механизмы execution host с `GIT_TERMINAL_PROMPT=0`; прогресс передаётся разобранными процентами через streaming RPC `git.mutationProgress`, без stderr/URL/секретов. `rejected`, `authentication`, известный `network` и `unknown-outcome` различаются; unknown не повторяется, UI перечитывает состояние. Force-push отсутствует.
- **Merge/rebase.** Требуют чистый index/worktree и отсутствие незавершённой операции. Конфликт возвращает `conflict` и свежее состояние, но не success; `RepositoryState.operationInProgress` вычисляется по Git-маркерам. Continue (`-c core.editor=true … --continue`) и Abort выбираются по фактическому типу операции, после чего маркеры перечитываются. Cherry-pick и resolver — вне этапа.
- **UI.** Popup: New Branch, Checkout, Merge/Rebase, Fetch/Push с явными remote/ref, прогресс, upstream/ahead/behind, время чтения refs/fetch, состояние незавершённой операции с Continue/Abort и notice. Все действия — native controls с `data-navigation-item`; ArrowDown из поиска ведёт к первой ref, стрелки/Tab достигают действий. Просмотр контекста и ref по-прежнему не меняет Git. Changes показывает незавершённую операцию и число конфликтов; черновики сохраняются по context ID.
- **Проверки.** Real Git: новый suite **13 passed**, pure units **7 passed**; прежние real-Git сценарии этапов 1–5 и broad transport/renderer regression — результаты и команды в STAGE6-REPORT.md. Web/node TypeScript, RPC catalog, targeted oxlint и Electron build — exit 0. Настоящий isolated Electron: stage-6 сценарии + соседние popup/catalog/diff/mutation/log/golden — результаты в STAGE6-REPORT.md.
- **Пределы.** Проверен только локальный macOS Electron с настоящими локальными bare remotes; SSH/WSL/Windows и release package не запускались. Теги можно checkout, но не создавать; push только локальных веток; fetch/push не рекурсируют в сабмодули; cherry-pick и полноценный conflict resolver — этап 8. Точные команды, сценарии и ограничения — STAGE6-REPORT.md. Этап 7 не начинался.

## Сквозные сценарии приёмки

1. **Ежедневный цикл:** popup → поиск сабмодуля → diff → stage нескольких строк → preview → commit; остальные изменения сохранены, index родителя не затронут.
2. **Связанные ревизии:** commit вложенного сабмодуля → gitlink и commit его родителя → gitlink и commit корня → публикация снизу вверх → чистый clone воспроизводит состояние.
3. **Конкурентный агент:** diff открыт → агент меняет тот же файл/index → старое частичное действие отклонено → новый diff показан без потери данных.
4. **Неинициализированное дерево:** запись видна до init, неизвестные потомки обозначены → явный init раскрывает структуру → обычная работа в дочернем контексте.
5. **Ограниченный checkout:** dirty/untracked или неопубликованные данные препятствуют update/remove → понятный отказ без force и без скрытого stash.
6. **Сбой сети:** часть пакетного push завершена → соединение потеряно → UI показывает известные/неизвестные результаты → сверка состояния вместо повторной публикации вслепую.
7. **Конфликт:** merge/rebase в сабмодуле → resolver → продолжение; отдельно конфликт gitlink в родителе → выбор результирующего дочернего OID.
8. **Изоляция worktree:** одна ветка занята другой рабочей копией, одинаковые имена сабмодулей и отдельные черновики → действия адресуются нужному контексту и корректно отказывают при ограничениях Git.

## Стратегия проверки

Постоянные тесты добавляются для потребительского поведения, границ и неопределённых преобразований: парсинг путей/статусов, частичный patch, stale-state, изоляция контекстов, порядок зависимых операций и ошибки. Интеграционные сценарии используют настоящий Git во временных репозиториях и локальные bare remotes, изолированные от пользовательских данных и конфигурации.

Smoke каждого этапа проходит через реальный UI Orca с последующей проверкой файлов/index/commit/refs. Если на текущем этапе нет нужного UI или доступа к execution host, соответствующий критерий не отмечается выполненным.

## За пределами обязательной поставки

Changelists и shelve остаются отдельным расширением архитектуры: именованные группы независимы от index, shelve не имитируется скрытым stash. Перед реализацией нужен отдельный план семантики пересекающихся групп, rename, устаревших hunks и восстановления. Их отсутствие не сокращает обязательную поддержку сабмодулей и popup из этапов выше.
